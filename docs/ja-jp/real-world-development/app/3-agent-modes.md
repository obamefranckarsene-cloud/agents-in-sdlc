まず、プロジェクトに小さな機能を追加しました。しかし、より大規模な変更には、さらに堅牢なプロセスが必要です。GitHub Copilot アプリは組織の既存のフローに沿って動作できるため、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント駆動型の開発プロセスを実践します。issue から新機能を作成し、コードが有効で、機能が期待どおりに動作することを確認して、最終的にプロジェクトにマージします。

> [!NOTE]
> 機能の作業を続ける間は、同じセッションを使用します。通常は作業するファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは主な概念に集中するため、手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub issue から新しいエージェント セッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新しい機能を実装します。
- コードをレビューします。
- ブラウザー キャンバスで機能を手動で検証します。

この機能の作業を続けながら、リポジトリの命令を更新し、既存の `quality-checks` スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能 PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者はカテゴリや発行元でゲームを絞り込む必要があります。バックログの issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細があります。Plan モードで方針を決めた後、範囲を限定した実装を Autopilot に許可します。

## 背景

AI コーディング エージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はより重要になります。多くの開発者は、次のようなフローで作業しています。

1. 必要な作業の詳細を記載した登録済みの issue を開きます。
2. 構築する内容の計画を立てます。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードがレビューされ、継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 詳細な手順はチームや組織によって異なりますが、ほとんどは上記の流れを基本にしています。

この標準的な方法に従えば、AI が生成したコードが要件を満たし、手書きのコードと同じレビュー プロセスを通るようにできます。

## セッション モード

**セッション モード**は、エージェントの自律性を制御します。プロンプト フィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと共同で作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが先に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントは完全に自律的に作業し、入力を待たずにコードを書き、テストを実行し、反復します。

Plan モードで開始して計画をレビューし、その後 Autopilot で実装します。

## issue からセッションを開始する

開始する前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリ フォルダーを選択し、リポジトリの上部ナビゲーションにある **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに含まれる issue です。新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選択します。

   ![GitHub Copilot アプリの issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モード セレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。通常のターミナルでは動作するのにセッションでは動作しない場合は、アプリの PATH またはバージョン マネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

Copilot がコードを書く前に、実装方法をレビューするため、計画を立てます。issue から始めたため、Copilot は機能リクエストをコンテキストとしてすでに把握しています。次のプロンプトを送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、issue の受け入れ基準と計画を照らし合わせます。カテゴリと発行元によるフィルター、アクセシブルなコントロール、データ アクセスの変更、テストが含まれることを確認します。複数カテゴリの組み合わせ方や、該当するゲームがない場合の動作など、不明確な内容について話し合います。

計画には、プロジェクトの既存ツールを使った lint、単体テスト、E2E テスト、型チェックを含めます。フィルターの実装とテストに範囲を絞り、品質ワークフローを完了してから PR を作成します。計画を承認する前に必要な変更を依頼し、後で検証するために issue の URL と合意事項を記録しておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンにある同等のオプションを選択します。承認しただけでモードが自動的に切り替わると思わず、アクティブなモードを確認してください。モード表示が **Autopilot** になっていることを確認します。

Copilot は実装に取りかかります。計画に沿ってコードを生成し、テストを実行しながら、処理を反復します。

> [!NOTE]
> 承認すると実装がすぐに始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポートの競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。自分が起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードは、他のコードと同じようにマージ前にレビューします。コードをレビューしてサイトを実行し、問題がないことを確認しましょう。

1. **Changes** を開き、フィルターの実装とテストを確認します。
2. 複数のカテゴリと発行元の組み合わせを含め、結果を issue と承認済みの補足事項に照らし合わせます。リポジトリの既存の命令に従っていることを確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、影響を受けるチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカル サーバーを再利用できます。以前のレッスンのサーバーではなく、この worktree のサーバーをテストしていることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くでしょうか。前と同じようにアプリを起動し、ブラウザー キャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザー キャンバスでページを開くよう Copilot に依頼します。

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. しばらくするとアプリが起動し、Copilot アプリ内にブラウザー ウィンドウが開きます。
3. カテゴリを選択して結果が一致することを確認します。フィルターを解除して発行元を選び、結果を確認します。
4. カテゴリと発行元のフィルターを組み合わせ、issue と承認済み計画に照らして結果を確認します。複数カテゴリに対応している場合は、合意した組み合わせ動作を確認します。
5. ゲームが一致しない組み合わせを試して、空の状態を確認します。フィルターを解除またはリセットし、一覧全体が戻ることを確認します。
6. 確認が終わったら、次のプロンプトで、このセッションに対して起動した開発サーバーを停止するよう Copilot に依頼します。

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 次のレッスンに備えてセッションを保持する

フィルターの PR はまだ作成またはマージしないでください。レッスン 4～8 でも、このセッション、worktree、ブランチを使います。次はカスタム命令をフィルターのコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で PR をまとめて作成してマージします。開発サーバーを停止した後はセッションをそのままにし、次のレッスンで同じセッションに戻ります。

エージェント モードを使って機能を構築し、レビューしました。このレッスンでは、次のことを行いました。

- GitHub issue から新しいエージェント セッションを開始しました。
- **Plan** モードで要件を定義しました。
- **Autopilot** モードで新機能を実装しました。
- コードをレビューしました。
- ブラウザー キャンバスで機能を手動で検証しました。

次は、[カスタム命令を使って][next-lesson]、コードの生成方法を指定し、文書化されたプラクティスに従っていることを確認します。
